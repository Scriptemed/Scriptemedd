# Single-file thesis defense presentation with animated robot arm

A self-contained 473-line HTML file implementing an 11-slide thesis defense presentation on "Direct Visual Servoing Using Multiscale Decomposition." The file bundles inline CSS (dark theme, slide transitions, 10 `@keyframes` for a robot arm power-on sequence, nth-child tag coloring) and inline JavaScript (keyboard/click navigation, canvas particle background). The design approach is a single `<section class="slide">` per topic, toggled via an `.active` class, with the robot animation gated by `#slide-2.active` selectors.

**Watch for:** Double percent signs (`%%`) throughout the CSS will be parsed as literal invalid values by browsers, breaking layout, backgrounds, and all keyframe stops (confirmed). Spark animations are declared in CSS with HTML-only properties (`position: absolute`, `box-shadow`) but the spark elements are SVG `<circle>` nodes where those properties have no effect (confirmed).

## High-level view

The robot arm animation uses staggered `animation-delay` values to sequentially reveal base, links, joints, and camera, with each segment picking up a persistent looping effect (energy pulse, joint glow spin, lens focus) once its reveal completes. The `forwards` fill-mode on reveal animations correctly keeps elements visible. Tag buttons use `nth-child` to assign four distinct solid colors (blue, green, amber, rose).

The CSS has a pervasive `%%` escaping issue that breaks every percentage-based value in the file — this is the primary blocker. The spark particle effect is architecturally mismatched: CSS rules target HTML layout properties on SVG elements where they don't apply, and the `transform-origin` for the orbit will reference (0,0) of the SVG viewport rather than the joint center.

## Double-percent CSS escaping

Every percentage value in the stylesheet is written as `%%` (e.g., `width: 100%%`, `height: 100%%`, gradient stops `#0f172a 0%%`, keyframe steps `0%%`, `50%%`, `100%%`). This is Python format-string escaping — the file was likely generated through a Python string template that doubled the percents. A browser will reject `100%%` as an invalid value and discard the entire declaration, meaning:

- `html, body` won't get `width: 100%` or `height: 100%`, breaking the viewport fill
- The dark gradient background won't render (invalid color stops)
- All `@keyframes` percentage stops become invalid, disabling every animation
- The progress bar width transition breaks

The JavaScript constructs `pct + '%'` correctly, so only the `<style>` block is affected. A global find-replace of `%%` with `%` fixes it.

## Spark animation mismatch (SVG vs HTML styling)

The CSS for `.spark`:

```css
position: absolute; width: 4px; height: 4px; border-radius: 50%;
background: #38bdf8; box-shadow: 0 0 6px #38bdf8, 0 0 12px #38bdf8;
animation: sparkOrbit 2s linear infinite;
```

The DOM elements:

```html
<circle class="spark spark-1" cx="200" cy="270" r="2" fill="#38bdf8"/>
```

SVG elements ignore `position`, `width`/`height`, `border-radius`, `background`, and `box-shadow`. The circles will render (they have `fill`), and `sparkOrbit`'s `transform` property does apply to SVG elements. But `transform-origin` for SVG defaults to the element's own (0,0) in its coordinate space, not the center of the circle. The orbit `rotate(0deg) translateX(12px) rotate(0deg)` will pivot around a point offset from the joint, producing an unexpected trajectory rather than a neat orbit around the joint center.

Fix options: set `transform-origin` to each spark's `cx`/`cy` explicitly (`transform-origin: 200px 270px`), or use `transform-box: fill-box` with `transform-origin: center`. Alternatively, replace with SVG-native `<animateTransform>`.

## SVG attribute vs CSS animation fragility

The FOV lines use inline SVG `opacity="0"` attributes and a CSS animation (`fovAppear`) that animates to `opacity: 0.6` with `forwards` fill. CSS animations override presentation attributes in the cascade, so this works in modern browsers. However, if the `%%` issue in the keyframe stops is fixed, these will animate correctly; as-is, the keyframe stops (`from`/`to` with `0%%`/`100%%`) are invalid and the animation won't run, leaving the lines permanently invisible.
